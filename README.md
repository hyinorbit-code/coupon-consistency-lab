# Coupon Consistency Lab

공지된 시각에 한정 수량의 경품 코드를 선착순으로 무료 배포하는 선착순 드롭을 소재로, 동시성 제어·성능 개선·장애 복구 후의 데이터 정합성을 직접 재현하고 측정하는 Java/Spring 백엔드 프로젝트입니다.
부하 테스트를 마친 뒤 실제 사용자 대상 이벤트로 검증하는 것이 목표입니다.
실제 사용자 대상 이벤트는 실제 커피 쿠폰 N매를 등록한 뒤, 커뮤니티 사이트와 무료 나눔 게시판에 홍보하고 실제로 들어오는 요청과 그 결과를 기록합니다.
이벤트 전에는 스트레스 테스트로 수천 건의 요청이 들어왔을 때 데이터 정합성이 지켜지는지 테스트 코드로 확인해 기록해 두고, 실제 사용자들이 참여했을 때의 결과와 비교합니다.

## 핵심 결과

| 문제 | 재현 | 해결 | 결과 |
| --- | --- | --- | --- |
| 동시 응모 시 경품 코드 중복 지급 | 코드 10개에 50명이 동시 응모하면 42명이 당첨 응답을 받음 | 비관적 락 → `FOR UPDATE SKIP LOCKED` | 당첨 응답 = 코드 수, 남의 코드를 받은 당첨자 0명 |
| 비관적 락의 데드락 | 1,000~5,000건마다 6~15건 데드락 (InnoDB 데드락 보고서로 원인 확인) | `SKIP LOCKED`로 대기 제거 | 데드락 0건, 5,000건 처리량 약 985/s → 1,200/s |
| 동시 첫 로그인 시 중복 가입 오류 | 같은 계정으로 20개 요청이 동시에 오면 9건이 500 오류 | DB 유니크 제약 + 새 트랜잭션에서 재조회 | 20건 모두 같은 사용자를 받음 |

- 모든 수치는 노트북 환경(애플리케이션 1개, MySQL 8.4 컨테이너, 서비스 직접 호출)의 측정값입니다. 측정 조건과 원본 결과는 docs/experiments/에 기록해 두었습니다.

## 만든 이유

4년 넘게 금융권 고객사에 B2B 보안 솔루션을 구축하고 운영해 왔습니다.
고객사마다 다른 인사·결재·인증 시스템과 연동하고 장애를 추적하는 일에는 익숙해졌지만, 솔루션은 고객사 내부 사용자가 쓰는 환경이라 많은 사용자가 같은 순간에 몰리는 상황을 다뤄 볼 기회가 없었습니다.

그래서 실무에서 비어 있던 부분을 직접 만들어 보기로 했습니다. 여러 요청이 같은 자원을 동시에 차지하려 할 때 데이터를 지키는 방법, 감이 아니라 같은 조건의 전후 숫자로 개선을 증명하는 습관, 그리고 부하 테스트에서 끝내지 않고 실제 사용자가 들어오는 이벤트를 직접 운영해 보는 경험을 쌓고 싶었습니다.

선착순 경품 배포를 고른 이유는 "코드 하나는 한 명에게만"이라는 규칙이 단순하면서도, 동시 요청에서 가장 쉽게 깨지기 때문입니다. 결제나 금전 지급은 다루지 않습니다.
또한 카카오 로그인 OAuth2를 활용하여 중복 상품 수령을 방지하고, 개인정보를 저장하지 않도록 설계했습니다.

## 진행 방식

혼자 하는 프로젝트라 "일단 되게 만들고 나중에 고치자"로 흘러가기 쉬워서, 처음부터 순서를 정해 두고 그대로 지키려고 했습니다.

1. 동시성 같은 건 신경 쓰지 않고, 일단 정확하게 동작하는 가장 단순한 버전을 만듭니다.
2. 문제가 있을 것 같으면 "아마 이럴 거야"로 넘어가지 않고, 실패하는 테스트로 먼저 증명합니다. 그리고 그 테스트를 수정보다 먼저 커밋합니다.
3. 고치는 방법이 여러 개면 같은 테스트, 같은 조건에서 돌려 보고 숫자로 비교합니다.
4. 고친 뒤에는 재현 테스트가 통과하는지, 다른 테스트가 깨지지 않았는지 확인합니다.
5. 결과와 그렇게 판단한 이유를 커밋 메시지와 실험 기록에 남깁니다.

Redis나 Kafka도 처음부터 넣지 않았습니다. 써 보고 싶은 마음은 있었지만, DB만으로 안 되는 지점을 직접 확인하기 전에 넣으면 "왜 썼냐"는 질문에 제대로 답할 수 없을 것 같았습니다.

## 동작 규칙

관리자가 이벤트를 만들고(초안), 경품 코드를 등록하고, 공개하면, 오픈 시각에 사용자들이 응모해서 선착순으로 코드를 하나씩 받는 흐름입니다.

구현하기 전에 "이건 어떤 상황에서도 깨지면 안 된다"는 규칙부터 적어 두었습니다. 테스트를 짤 때도, 실험 결과를 볼 때도 결국 이 다섯 가지가 지켜졌는지를 봤습니다.

1. 할당된 코드 수는 등록된 코드 수를 넘지 않는다.
2. 코드 하나는 최대 한 명에게만 간다.
3. 한 사람은 이벤트 하나에서 최대 한 번만 당첨된다.
4. 당첨 기록과 코드 할당은 항상 같이 존재한다.
5. 재처리나 재시작을 해도 당첨자가 바뀌지 않는다.

세부 규칙을 정하면서 고민했던 내용들입니다.

- 선착순 기준은 서버가 커밋한 순서로 잡았습니다. 클라이언트가 보낸 시각은 조작할 수 있어서 믿지 않습니다.
- 같은 사람이 버튼을 다시 누르면 처음 받은 경품을 그대로 돌려줍니다. `(이벤트, 사용자)` 유니크 제약이 그대로 멱등 키 역할을 해서, 따로 멱등 키 헤더를 만들 필요는 없었습니다.
- 이벤트 기간은 `[오픈, 종료)`로 잡았습니다. 정확히 오픈 시각이면 진행 중이고, 정확히 종료 시각이면 끝난 겁니다. 이 경계는 1나노초 단위로 테스트해 두었습니다.
- 코드 등록, 공개, 취소는 오픈 전에만 됩니다. 오픈한 뒤에 수량이 바뀌면 먼저 온 사람과 나중 온 사람의 조건이 달라지고, 당첨을 취소하는 기능도 두지 않기로 했기 때문입니다.
- 매진이나 종료 응답은 DB에 남기지 않습니다. 매진 직후에 몰리는 요청까지 전부 INSERT하면 그게 오히려 부하가 되기 때문입니다. 그러다 보니 참여 기록 테이블을 따로 둘 이유가 없어졌고, "코드 행에 사용자가 채워져 있으면 당첨"으로 표현했습니다. 당첨과 할당이 같은 행이라 4번 규칙은 구조상 깨질 수가 없습니다.

## 사례 1: 동시 응모 시 코드 중복 지급

### 첫 구현과 문제 재현

처음에는 "아직 안 나간 코드 중 id가 제일 작은 걸 조회하고, 거기에 사용자를 넣어 저장"하는 식으로 만들었습니다. 요청이 하나씩 올 때는 아무 문제가 없었습니다.

일부러 이 상태로 동시 요청 테스트를 돌려 봤는데, 생각보다 훨씬 심했습니다. 코드 10개에 50명이 동시에 응모하자 42명이 "당첨" 응답을 받았습니다. 정작 DB에 남은 당첨은 10건뿐이었습니다. 다들 같은 첫 번째 코드를 읽어 가서 각자 UPDATE를 했고, 나중에 쓴 사람이 앞사람의 당첨을 덮어쓴 겁니다. 앞사람은 이미 "당첨, 코드는 ○○○"라는 응답을 받은 뒤였습니다. 실제 이벤트였다면 커피 쿠폰 10장의 코드를 40명 넘게 받아 가고, 30명 넘는 사람이 "쿠폰이 안 돼요"라고 연락하는 상황입니다.

### 비관적 락

가장 직관적인 방법부터 해 봤습니다. 코드를 조회할 때 `SELECT ... FOR UPDATE`로 잠그도록 바꿨습니다. 
같은 사람이 동시에 여러 번 누르는 경우는 `UNIQUE(이벤트, 사용자)` 충돌이 나면 새 트랜잭션에서 기존 당첨을 다시 조회해 돌려주도록 했습니다.

결과는 반반이었습니다.

- 남의 코드를 받는 사람은 5,000건 규모에서도 0명이 됐습니다.
- 잠그면 느려질 줄 알았는데 처리량이 오히려 15~20% 올랐습니다. 잠금이 없을 때는 이미 나간 코드에 UPDATE가 계속 몰렸는데, 잠그고 나니 매진이 빨리 확정돼서 쓰기 없이 끝나는 요청이 많아졌기 때문이었습니다.
- 대신 처음 보는 문제가 생겼습니다. 1,000~5,000건마다 6~15건씩 데드락이 났습니다. 데이터는 롤백되니까 틀리지는 않지만, 그 사람은 당첨도 매진도 아닌 오류를 받습니다.

### 데드락 원인 분석

처음엔 "락을 쓰니까 데드락도 나겠지" 정도로 생각했는데, 그렇게 넘기면 다음에 같은 문제를 만나도 설명을 못 할 것 같았습니다. 
그래서 테스트 중에 데드락을 일부러 일으키고 `SHOW ENGINE INNODB STATUS`로 MySQL이 남긴 데드락 보고서를 직접 뽑아 봤습니다.

보고서를 보니 같은 코드 행(id 7)을 두고 두 트랜잭션이 서로 반대 순서로 잠금을 잡으려 하고 있었습니다.

- 트랜잭션 1은 기본키 레코드를 먼저 잡고, UPDATE하면서 보조 인덱스 레코드를 기다리고 있었습니다.
- 트랜잭션 2는 보조 인덱스 레코드를 먼저 잡고, 기본키 레코드를 기다리고 있었습니다.

더 의외였던 건 그 보조 인덱스였습니다. `fk_prize_codes_assigned_user`라는 인덱스였는데, 제가 스키마에 만든 게 아니라 외래키를 걸면서 MySQL이 알아서 만든 인덱스였습니다. 
할당할 때 이 인덱스의 키 값(`assigned_user_id`)이 NULL에서 사용자 id로 바뀌니까, 잠가야 할 레코드가 하나 더 생긴 셈입니다.

### SKIP LOCKED 적용

다시 생각해 보니 이 문제는 "남은 수량 숫자 하나를 깎는" 구조가 아니었습니다. 서로 다른 코드 N개를 한 명씩 나눠 주는, 작업 큐에서 일감을 하나씩 가져가는 구조에 가까웠습니다. 
그렇다면 잠긴 코드를 굳이 기다릴 필요 없이 다음 코드를 가져가면 됩니다. 그래서 `FOR UPDATE SKIP LOCKED`로 바꿨습니다.

같은 조건에서 세 방식을 연달아 돌린 결과입니다(5,000건, 코드 500개).

| 방식 | 걸린 시간 | 처리량 | p50 | 데드락 | 정확성                 |
| --- | --- | --- | --- | --- |---------------------|
| 잠금 없음 | 약 6.2초 | 약 810/s | 약 72ms | 0 | 약 1,590명이 남의 코드를 받음 |
| 비관적 락 | 약 5.1초 | 약 985/s | 약 29ms | 8~9건 | 데드락 발생              |
| SKIP LOCKED | 약 4.2초 | 약 1,200/s | 약 12ms | 0 | 전체 통과               |

재현 테스트는 10번 연달아 통과했고, 1,000건부터 5,000건까지 모든 시나리오에서 데드락이 한 번도 나지 않았습니다.

### 추가 비교 계획

조건부 UPDATE 한 문장(`UPDATE ... WHERE assigned_user_id IS NULL ORDER BY id LIMIT 1`)과 Redis 선차감도 같은 조건에서 비교해 보려고 합니다. 
지금 숫자는 앱 하나에서 서비스를 직접 호출한 결과라, 배포한 뒤에 여러 인스턴스와 HTTP 부하(k6)로도 다시 측정할 계획입니다.

## 그 밖의 고민

### 동시 첫 로그인 오류

응모보다 먼저 겪은 동시성 문제였습니다. 같은 외부 계정으로 첫 로그인 요청이 동시에 여러 개 들어오면, 다들 "아직 없는 사용자네" 하고 INSERT를 해서 일부가 유니크 충돌로 500이 났습니다. 20건 중 9건이었습니다.
"조회해서 없으면 저장"은 애플리케이션 코드만으로는 경쟁 조건을 막을 수가 없었습니다. 
그래서 누가 먼저인지는 DB 유니크 제약에 맡기고, 애플리케이션은 충돌이 나면 복구만 하도록 바꿨습니다.

### 사용자와 로그인 수단 분리

한 사람이 이메일로도, 카카오로도 로그인할 수 있게 하려고 `users`와 `user_identities`를 나눴습니다. `UserIdentity`가 `@ManyToOne`으로 `User`를 바라보고, `(제공자, 제공자 사용자 ID)`에 유니크 제약을 걸어서 같은 카카오 계정이 두 사용자에 붙지 않게 했습니다.

로그인 수단과 응모 자격도 따로 보기로 했습니다. 이메일은 `+`나 `.`을 붙이거나 일회용 메일을 쓰면 계정을 사실상 무한히 만들 수 있어서, 응모는 카카오 계정을 연동한 사람만 할 수 있게 할 계획입니다.

### 모듈 간 순환 의존

이벤트(`drop`)와 경품 코드(`prizecode`)는 모듈을 나눠 두었습니다. 코드를 등록할 때 "이벤트가 아직 오픈 전인지" 알아야 해서 이미 `prizecode`가 `drop`을 참조하고 있었습니다. 
그런데 공개 기능을 만들면서 "코드가 0개면 공개를 막자"는 규칙을 넣으려니, 이번엔 `drop`이 코드 개수를 알아야 했습니다.

`drop`이 `prizecode`를 그냥 불러 버리면 서로를 참조하는 순환이 생기고, Spring Modulith 검증 테스트가 바로 실패합니다. 
그래서 `drop` 쪽에 `PrizeCodeQuery`라는 인터페이스를 만들어 두고, 구현은 `prizecode`가 하게 했습니다. 이렇게 하면 `drop`은 인터페이스만 알고, 참조 방향은 여전히 `prizecode → drop` 한쪽입니다.

### 경품 코드 암호화 저장

경품 코드는 그 자체로 바로 쓸 수 있는 쿠폰이라, DB가 털려도 원문이 보이면 안 된다고 생각했습니다.

- 원문은 AES-GCM으로 암호화해서 저장합니다. 매번 새 IV를 쓰기 때문에 같은 코드라도 암호문이 매번 다릅니다.
- 그런데 암호문이 매번 다르면 "이미 등록된 코드인지" 비교할 수가 없습니다. 그래서 중복 검사는 별도 키로 만든 HMAC-SHA256 해시로 합니다. 키 없는 SHA-256을 쓰면 코드 형식이 단순할 때 가능한 값을 전부 넣어 보는 식으로 원문을 알아낼 수 있어서 HMAC을 골랐습니다.
- 두 키는 저장소에 넣지 않고 환경변수로만 받습니다. 키가 없거나 길이가 안 맞으면 서버가 아예 뜨지 않게 해서, 설정 실수를 배포할 때 바로 알 수 있게 했습니다. 원문은 당첨된 본인 응답에만 복호화해서 넣습니다.

### 엔티티와 스키마 검증

`ddl-auto`를 `validate`로 두고, 스키마 변경은 Flyway로만 합니다. 실제로 덕을 본 적이 있습니다. `BINARY(32)` 컬럼을 `byte[]`로 매핑했더니 Hibernate는 `VARBINARY`를 기대하고 있어서 앱이 기동 단계에서 실패했습니다. `update`로 뒀다면 조용히 넘어가서 운영에서야 이상하다는 걸 알았을 수도 있습니다. `@JdbcTypeCode(SqlTypes.BINARY)`를 붙여서 고쳤습니다.

### 계층 규칙 테스트

ArchUnit으로 "서비스는 DTO를 모른다", "엔티티는 리포지토리나 서비스를 모른다", "공통 모듈은 도메인 모듈을 모른다" 같은 규칙을 검사하고 있습니다. 관리자 API를 만들 때 서비스가 요청 DTO를 그대로 받게 짰다가 이 테스트에 걸렸습니다. 그래서 서비스는 값과 엔티티만 다루고, DTO 변환은 컨트롤러가 하도록 바꿨습니다. 귀찮다고 생각했는데, 나중에 동시성 테스트를 짤 때 서비스를 DTO 없이 바로 호출할 수 있어서 오히려 편했습니다.

## 구조

```
io.github.hyinorbitcode.couponlab
├── global/        공통: 오류 응답, 시계, /api 경로, 보안 응답 처리
├── user/          사용자·인증 (외부 계정 연동, JWT, 실험용 토큰)
├── drop/          이벤트: 생성·공개·취소, 기간 판정
├── prizecode/     경품 코드: 암호화 등록, 선착순 할당
└── participation/ 응모: 순서 조율 (이벤트 확인 → 기존 당첨 → 기간 → 할당)
```

- 모듈러 모놀리스로 시작했습니다. 처음부터 서비스를 나누면 다룰 게 너무 많아져서, 모듈 경계만 확실히 지키고 나중에 정말 나눌 이유가 생기면 그때 나누려고 합니다. 각 모듈은 바로 아래 패키지에 둔 타입(`CurrentUser`, `DropEventApi`, `PrizeCodeAssigner` 같은 것)만 다른 모듈에 보여 주고, 그 아래 `controller`, `service`, `repository`, `entity`, `dto`, `exception`, `config`는 모듈 안에서만 씁니다. Spring Modulith가 이 경계를 테스트로 검사합니다.
- 오류 응답은 전부 `ProblemDetail`에 `code`를 붙여서 내려줍니다(`SOLD_OUT`, `DROP_NOT_OPEN` 같은 식). 프론트에서 메시지가 아니라 코드로 분기할 수 있게 하려는 것입니다.
- 인증은 무상태 JWT(HS256)입니다. 컨트롤러에서는 `CurrentUser` 파라미터 하나로 로그인한 사용자를 받습니다. 카카오 로그인을 붙이기 전까지는 `experiment` 프로필에서만 열리는 실험용 토큰 발급 API로 테스트합니다.

## 테스트

- 단위·통합 테스트가 199개 있습니다. 엔티티 규칙, API 응답, 권한, 오류 코드, 아키텍처 규칙까지 봅니다. 통합 테스트는 Testcontainers로 실제 MySQL을 띄워서 돌립니다. H2 같은 걸 쓰면 이번 데드락처럼 MySQL에서만 생기는 문제를 놓칠 수 있어서입니다.
- 동시성 테스트는 `@Tag("concurrency")`로 따로 빼서 `concurrencyTest`로 돌립니다. 스레드를 `CountDownLatch`로 한꺼번에 출발시키고, 위의 불변식이 지켜졌는지 확인합니다.
- `EntryStressTests`는 `STRESS=true`일 때만 돌아가는 측정용 테스트입니다. 1,000~5,000건 시나리오에서 처리량, 지연, 데드락, 정확성을 출력합니다.

## 실행 방법

JDK 25(Gradle toolchain이 알아서 찾습니다)와 Docker 런타임(Testcontainers가 MySQL 8.4 컨테이너를 띄웁니다)이 필요합니다.

```bash
./gradlew test             # 단위·통합 테스트
./gradlew concurrencyTest  # 동시성 테스트 ("concurrency" 태그)
./gradlew check            # 전체
./gradlew bootTestRun      # Testcontainers MySQL과 함께 로컬 실행 (test·experiment 프로필)
```

```bash
STRESS=true ./gradlew concurrencyTest --tests '*EntryStressTests'   # 스트레스 측정
```

로컬에서 띄운 뒤에는 실험용 토큰 발급 API로 토큰을 받아서 다른 API를 호출해 볼 수 있습니다. 이 API는 `experiment` 프로필에서만 열립니다.

```bash
curl -s -X POST localhost:8080/api/experiment/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"providerUserId":"u-1","nickname":"tester","role":"USER"}'
```

실행 중인 MySQL 컨테이너에 들어가 보려면:

```bash
docker exec -it $(docker ps -q --filter ancestor=mysql:8.4 | head -1) mysql --default-character-set=utf8mb4 -utest -ptest test
```

실제 환경에서는 아래 환경변수가 있어야 뜹니다. API는 전부 `/api` 아래에 있습니다(`/actuator` 제외).

| 환경변수 | 내용 |
| --- | --- |
| `COUPONLAB_AUTH_JWT_SECRET` | JWT 서명 키, 32바이트 이상 |
| `COUPONLAB_PRIZE_CODE_ENCRYPTION_KEY` | 경품 코드 암호화 키, 32바이트 base64 |
| `COUPONLAB_PRIZE_CODE_HASH_KEY` | 경품 코드 중복 검사용 HMAC 키, 32바이트 base64 (암호화 키와 달라야 합니다) |

```bash
cd frontend && npm install && npm run dev   # http://localhost:5173, /api는 8080으로 프록시
```
