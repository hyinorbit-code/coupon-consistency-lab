# ADR-0003 업무 규칙 (0단계)

작성일: 2026-10-30
상태: 채택
일부 대체: 규칙 1의 참여 자격은 ADR-0010으로 대체됨(카카오 연동 사용자만 응모, 카카오 계정당 1회)

## 맥락

ADR-0002로 도메인을 선착순 무료 드롭으로 바꿨다. PROJECT_PLAN 4절의 0단계 확정 항목(1차 마일스톤에 필요한 규칙)과, 이벤트 설계 방향에 영향을 주는 E단계 규칙 일부를 확정한다.

## 도메인 골격

| 개념 | 핵심 속성 |
| --- | --- |
| 이벤트 | 오픈 시각, 종료 시각, 경품 설명, 상태 |
| 경품 코드 | 이벤트, 코드(암호화 저장), 할당 여부, 할당된 사용자, 할당 시각 |
| 참여 기록 | 이벤트, 사용자, 결과, 처리 시각 |
| 사용자 | 카카오 회원번호, 닉네임, 역할 |

총 수량은 따로 저장하지 않는다. 등록된 코드 개수가 곧 수량이므로 수량과 실제 코드가 어긋날 수 없다.

## 규칙

### 1. 참여 제한과 멱등성
- 카카오 계정당 이벤트 1회. `(이벤트, 사용자)` 유니크 제약으로 강제한다.
- 같은 사용자의 재요청에는 이미 기록된 결과(당첨이면 같은 코드)를 그대로 반환한다.
- 이 자연 키가 멱등 키이므로 `Idempotency-Key` 헤더는 쓰지 않는다.

### 2. 선착순 판정
- 순서는 서버가 커밋한 순서다. 클라이언트가 보낸 시각은 무시한다.
- 오픈 여부는 DB 시각으로 판정해 인스턴스 간 시계 차이를 배제한다.
- 오픈 전 요청은 "아직 열리지 않음"으로 거절하고 참여 기록을 남기지 않는다. 미리 누른 사용자가 참여 기회를 잃지 않게 한다.
- 종료 후 요청은 "종료", 할당할 코드가 없으면 "매진"으로 응답한다.
- 매진·종료 응답은 참여 기록으로 남기지 않는다. 매진 뒤 몰리는 요청이 매번 쓰기를 일으키지 않게 하고, 참여 시도 수는 메트릭으로 센다. 따라서 참여 기록은 당첨자 기록이다.

### 3. 당첨과 코드 할당
- 당첨 기록 생성과 코드 할당은 같은 트랜잭션에서 처리한다.
- 할당할 수 있는 코드가 없으면 매진이다.
- 당첨 취소와 코드 반환은 없다.
- 3단계(사례 1)에서 비교할 할당 방식: 조건부 UPDATE, 비관적 락(`SELECT … FOR UPDATE`), `SKIP LOCKED`, Redis 선차감 후 DB 할당.

### 4. 시간
- UTC로 저장(`Instant`, MySQL `DATETIME(6)`)하고 Asia/Seoul로 표시한다.
- 이벤트 기간은 반열린 구간 `[오픈, 종료)`다.

### 5. 경품 코드 보관과 조회
- 코드는 애플리케이션에서 AES로 암호화해 저장한다. 키는 환경변수로 주입하고 저장소에 넣지 않는다.
- 코드 원문은 당첨된 본인만 조회한다. 관리자 화면에서는 일부를 가린다.

### 6. 권한과 계정
| 역할 | 권한 |
| --- | --- |
| ADMIN | 이벤트 생성, 코드 일괄 등록, 결과·통계 조회 |
| USER | 이벤트 조회, 참여, 본인 당첨 코드 조회 |

- 실서비스: 카카오 로그인으로 사용자를 만들고 자체 JWT를 발급한다. 카카오 로그인 연동은 E단계에서 구현한다.
- 실험: `experiment` 프로필에서만 열리는 토큰 발급 엔드포인트와 대량 시드 스크립트로 계정을 만든다. 1~3단계는 이것만으로 진행한다.

### 7. 오픈 전 로그인 유도 (E단계 방향)
- 오픈 정각에 카카오 로그인 리다이렉트가 몰리면 외부 의존성이 병목이 되므로, 이벤트 페이지에서 미리 로그인하도록 안내한다.
- 대기 화면은 로그인한 상태에서 카운트다운을 보여준다.

## 불변식

테스트와 실험의 판정 기준이다.

1. 할당된 코드 수 ≤ 등록된 코드 수
2. 코드 하나는 최대 한 명에게 할당된다.
3. 사용자당 이벤트별 당첨은 최대 1회다.
4. 당첨 기록과 코드 할당은 항상 함께 존재한다.
5. 재처리·재시작 전후 당첨자 집합이 바뀌지 않는다.

## 나중에 확정할 것

- E단계 직전: 대기열 도입 여부, 요청 속도 제한 기준, 봇·다중 계정 대응, 개인정보 보관 기간과 파기 절차, 이벤트 공지·약관 문구
- 5~6단계 직전: 참여 접수의 비동기 전환 여부와 접수·판정·실패 상태 및 조회 계약
