# ADR-0002 도메인 전환: 선착순 무료 드롭과 실전 이벤트

작성일: 2026-10-30
상태: 채택
보강: 2026-10-30 로그인 수단을 카카오 하나로 제한하는 근거 추가 (결정 변경 없음)

## 맥락

초기 계획의 도메인은 할인 쿠폰의 발급·사용·취소·만료와 가맹점별 정산이었고, 모든 부하·장애 결과를 통제된 실험으로만 얻도록 했다. 이 경우 가장 큰 갭인 "실사용자 트래픽 운영 경험"은 프로젝트로 메울 수 없다.

커뮤니티에 오픈 시각을 공지하고 실제 경품을 선착순으로 무료 배포하면, 규모는 작더라도 실제 사용자의 순간 피크 트래픽을 운영한 결과를 얻을 수 있다.

## 결정

1. 도메인을 **선착순 무료 드롭 + 경품 코드 지급**으로 바꾼다. 할인 계산, 가맹점, 부담 비율, 정산은 범위에서 뺀다.
2. 통제된 실험(1~4단계)을 마친 뒤 **실전 이벤트 단계(E)**를 둔다. 사전 부하 테스트 → 1회차 소규모 리허설 → 2회차 본 이벤트 → 회고 순서로 진행한다.
3. 이벤트 구성:

| 항목 | 결정 |
| --- | --- |
| 로그인 | 카카오 로그인. 회원번호와 닉네임만 받는다 |
| 참여 제한 | 카카오 계정당 이벤트 1회 |
| 경품 | 2천 원 커피 쿠폰 10매(회차당 약 2만 원). 코드를 미리 구매해 등록한다. 규모는 1회차 결과를 보고 조정한다 |
| 지급 | 앱 화면에 바코드 표시 + 카카오톡 공유 버튼(사용자가 직접 전송) |
| 개인정보 | 휴대폰 번호·이메일을 받지 않는다. 보관 기간과 파기 기준을 공지한다 |

## 근거

- 실제 사용자 수가 수백~수천 명 수준이어도, 정각에 몰리는 짧은 피크는 정합성이 깨지기 쉬운 조건이라 검증 가치가 있다.
- 사례 3개(동시성, 성능, 장애 복구)의 구조는 유지된다. 정산 대신 "코드가 정확히 한 명에게 한 번만 할당되는가"가 정합성의 핵심이 되며, 중복 할당은 실제 손실이다.
- 가맹점·할인·정산의 복잡도가 빠지고 대기열, 봇·어뷰징 방어, 실전 모니터링이 들어온다.

## 로그인 수단을 카카오 하나로 제한하는 이유

"계정당 1회" 제한은 실제로는 사람이 아니라 `(인증 제공자, 제공자 회원번호)` 단위다. 카카오와 네이버처럼 제공자가 둘이면 같은 사람이 계정마다 따로 참여해 경품을 두 개 가져갈 수 있다. 카카오 회원번호와 네이버 회원번호 사이에는 같은 사람임을 알려 줄 공통 식별자가 없다.

| 방법 | 제공자를 넘나드는 중복 방지 | 비용 |
| --- | --- | --- |
| **로그인 수단을 카카오 하나로 제한 (채택)** | 원천 차단 | 없음 |
| 제공자마다 휴대폰 번호를 받아 해시로 비교 | 차단 | 민감 개인정보 수집. 카카오는 비즈 앱 전환과 검수 필요 |
| 휴대폰 본인인증(PASS 등) CI로 사람 단위 식별 | 가장 확실 | 건당 비용, 사업자 계약, 무거운 개인정보 처리. 개인 프로젝트에 비현실적 |

- 회차당 경품이 약 2만 원이므로 완벽한 신원 확인에 드는 비용과 개인정보 부담이 얻는 것보다 훨씬 크다.
- 카카오 하나로도 한 사람이 여러 카카오 계정을 가질 수 있다. 다만 카카오 계정은 보통 휴대폰 번호와 묶여 있어 여러 개를 만들기 번거롭고, 이 정도 잔여 위험은 받아들인다.
- 잔여 다중 계정 위험은 E단계에서 탐지하고 기록한다(예: 같은 IP·기기에서 짧은 시간에 여러 계정이 당첨되는 패턴). 결과는 이벤트 회고의 어뷰징 분석에 남긴다.
- 다른 로그인 수단을 추가하려면 먼저 제공자를 넘나드는 사람 단위 식별 방법을 정해야 하며, 그때 새 ADR로 결정한다.

공정성(1인 1회)과 개인정보 최소 수집 사이의 트레이드오프로, 로그인 수단을 하나로 제한해 제공자를 넘나드는 중복을 원천 차단하고 남는 위험은 경품 규모에 맞춰 탐지·기록으로 대응한다.

## 검토 후 기각한 대안

- **카카오톡 메시지 API로 서버가 직접 발송**: 카카오 문서상 메시지 API는 같은 서비스 내 사용자 간 발송만 지원하며 서비스가 사용자에게 보낼 수 없다. 서비스 발송은 알림톡·브랜드 메시지 대상인데, 카카오톡 채널과 카카오비즈니스 절차, 발송 비용이 필요해 개인 프로젝트에 과하다.
- **기프티콘 발송 API 연동**: B2B 계약이 필요하다.
- **휴대폰 번호를 받아 문자 발송**: 개인정보 처리 부담이 커진다.

## 설계 원칙

돈이 걸린 상태 변경(코드 할당)은 시스템 안에서 정확히 한 번만 일어나게 하고, 알림·전달은 중복돼도 같은 코드라 손실이 없게 분리한다. 나중에 실제 발송 채널을 붙여도 이 구조를 유지한다.

## 결과

- PROJECT_PLAN의 배경·목표·범위·업무 규칙·단계·마일스톤을 무료 드롭 기준으로 개정한다.
- 정직성 원칙을 "실사용자를 다루지 않는다"에서 "소규모 실사용자 이벤트를 운영하고, 실측 결과와 통제된 실험 결과를 구분해 기록한다"로 바꾼다.
- 이벤트 전에 확인할 것: 회사 취업규칙의 겸업·외부 활동 조항, 홍보할 커뮤니티의 홍보 글 규정, 개인정보 처리방침 게시.
