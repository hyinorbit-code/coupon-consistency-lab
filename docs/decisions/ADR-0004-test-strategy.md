# ADR-0004 테스트 전략

작성일: 2026-10-30
상태: 채택

## 맥락

테스트 코드와 테스트 기준은 이 프로젝트가 메우려는 가장 큰 갭 중 하나다(PROJECT_PLAN 1절). ADR-0003의 업무 규칙과 불변식을 실행 가능한 형태로 검증하고, 3단계 동시성 사례의 출발점이 되는 재현 테스트를 만들 수 있어야 한다.

## 원칙

- **불변식이 판정 기준이다.** ADR-0003의 불변식 5개는 모두 테스트 코드로 존재한다.
- **DB 동작이 중요한 곳은 실제 MySQL로 검증한다.** H2나 목으로 락·유니크 제약·트랜잭션을 흉내 내지 않는다.
- **목은 외부 경계에만 쓴다.** 카카오 API, 시계 등. 내부 리포지토리는 목으로 대체하지 않는다.

## 테스트 계층

| 계층 | 대상 | 도구 | 비중 |
| --- | --- | --- | --- |
| 단위 | 도메인 규칙: 기간 판정 `[오픈, 종료)`, 상태 전이, 코드 마스킹, 암호화 왕복 | JUnit 5, AssertJ. 스프링 없이 실행 | 많음, 빠름 |
| 모듈 통합 | 모듈 단위 기능 흐름: 참여 → 할당 → 조회, 유니크 제약, 트랜잭션 롤백 | `@ApplicationModuleTest` + Testcontainers MySQL | 핵심 |
| 경계 검증 | 모듈 간 의존 규칙 | Spring Modulith `ApplicationModules.verify()` | 1개 |
| API | 요청·응답 계약, 권한, 에러 코드 | MockMvc 또는 RestTestClient + Testcontainers | 주요 엔드포인트만 |
| 동시성 | 불변식 1~4가 동시 요청에서 유지되는지 | 다중 스레드(`ExecutorService` + `CountDownLatch`) + Testcontainers | 할당 방식마다 |
| 부하·장애 | 처리량, 지연, 장애 주입 | k6, Docker Compose | 테스트 코드가 아니라 3단계 이후 **실험**으로 분리 |

## 동시성 테스트

1. 코드 N개(예: 10개)를 등록한다.
2. 서로 다른 사용자 M명(예: 200명)이 `CountDownLatch`로 출발을 맞춰 동시에 참여한다.
3. 같은 사용자가 여러 번 동시에 요청하는 경우를 별도로 만든다.
4. 결과는 DB에서 직접 검증한다: 할당 수 ≤ N, 코드 중복 0, 사용자당 당첨 1회 이하, 당첨 기록과 할당 일치.
5. 3단계에서는 제어 없는 구현이 이 테스트에서 실패하는 것을 먼저 확인한 뒤, 할당 방식 4가지(조건부 UPDATE, 비관적 락, `SKIP LOCKED`, Redis 선차감)가 모두 통과하는지 본다.

단일 프로세스 다중 스레드 테스트는 정확성 검증용이다. 다중 인스턴스 환경은 k6 실험에서 다룬다.

## 시간

- `Clock`을 주입해 쓰고, 테스트에서는 고정 시각으로 오픈 전·종료 경계를 검증한다.
- 오픈 판정은 DB 시각 기준(ADR-0003)이므로, 통합 테스트에서는 이벤트의 오픈·종료 시각을 DB 현재 시각 기준으로 설정해 검증한다.

## 실행과 속도

- Testcontainers 컨테이너는 테스트 전체에서 하나를 재사용한다(싱글턴 컨테이너).
- 테스트 간 격리는 트랜잭션 롤백이 아니라 테이블 초기화로 한다. 동시성 테스트는 여러 트랜잭션이 실제로 커밋되어야 하기 때문이다.
- Gradle에서 JUnit 태그로 `test`(단위 + 통합)와 `concurrencyTest`(무거운 동시성 테스트)를 나눈다. CI에서는 둘 다 실행한다.

## 커버리지 기준

- 라인 커버리지 수치는 목표로 삼지 않는다.
- 완료 기준은 **규칙 하나당 테스트 1개 이상**, **불변식은 모두 동시성 테스트로 검증**이다.
- JaCoCo 리포트는 참고용으로 생성한다.

## 테스트 이름

- `@DisplayName`에 한글로 규칙을 문장으로 쓴다. 예: "오픈 전 요청은 거절되고 참여 기록이 남지 않는다"
- 테스트 목록이 ADR-0003의 실행 가능한 명세가 되도록 한다.

## 검토 후 기각한 대안

- **H2 인메모리 DB**: 락·격리 수준·`SKIP LOCKED` 동작이 MySQL과 달라 동시성 검증이 무의미해진다.
- **트랜잭션 롤백 기반 격리(`@Transactional` 테스트)**: 동시성 테스트에서 커밋이 일어나지 않아 실제 경합을 재현할 수 없다.
- **라인 커버리지 목표치**: 수치를 맞추려는 의미 없는 테스트를 부른다.
