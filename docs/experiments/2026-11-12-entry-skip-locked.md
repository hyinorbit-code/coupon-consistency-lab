# 실험 기록: 응모 할당에 SKIP LOCKED 적용 (2026-11-12)

비관적 락에서 남은 데드락을 없애기 위해 미할당 코드 조회를 `FOR UPDATE SKIP LOCKED`로 바꾸고, 같은 조건에서 세 방식(잠금 없음, 비관적 락, SKIP LOCKED)을 다시 측정했다. 이전 기록: [비관적 락](2026-11-12-entry-pessimistic-lock.md).

## 바꾼 것

```java
// PrizeCodeRepository
@Query(value = """
        select * from prize_codes
        where drop_event_id = :dropEventId
          and assigned_user_id is null
        order by id
        limit 1
        for update skip locked
        """, nativeQuery = true)
Optional<PrizeCode> findFirstAvailableForUpdateSkipLocked(@Param("dropEventId") long dropEventId);
```

- `PrizeCodeAssignService.assign()`이 이 메서드를 쓰도록 한 줄 바꿨다.
- 비관적 락 메서드(`findFirstForUpdate...`)와 잠금 없는 메서드는 비교용으로 남겨 두었다.
- 같은 사용자 중복 처리(`UNIQUE` 충돌 시 기존 당첨 재조회)는 그대로다.

## 측정 환경

이전 기록과 같다. MacBook 8코어, MySQL 8.4(Testcontainers·OrbStack), 애플리케이션 1개, 서비스 직접 호출, HikariCP 커넥션 10개.
세 방식을 **같은 세션에서 연달아** 측정했다(SKIP LOCKED 2회, 비관적 락 1회, 잠금 없음 1회). 비교용 측정은 서비스 코드를 잠시 바꿔 실행한 뒤 되돌렸다.

## 요약 (S3, 5,000건 / 코드 500 기준, 각 방식 측정값의 평균)

| 방식 | 걸린 시간 | 처리량 | p50 | 데드락 | 정확성 |
| --- | --- | --- | --- | --- | --- |
| 잠금 없음 | 약 6.2초 | 약 810/s | 약 72ms | 0 | ❌ 당첨자 약 1,590명이 남의 코드를 받음 |
| 비관적 락 | 약 5.1초 | 약 985/s | 약 29ms | 8~9건 | ✅ 단, 데드락 요청은 오류로 끝남 |
| **SKIP LOCKED** | **약 4.2초** | **약 1,200/s** | **약 12ms** | **0** | ✅ |

- SKIP LOCKED는 비관적 락보다 처리량이 **약 22% 높고**, 중간 지연(p50)은 **절반 이하**였다. 잠금 없음보다는 처리량이 약 48% 높았다.
- **데드락은 모든 시나리오, 2회 실행, 재현 테스트 10회 반복에서 0건**이었다.

## 해석

1. **데드락이 사라진 이유:** 비관적 락의 데드락은 두 트랜잭션이 같은 코드 행의 기본키 레코드와 보조 인덱스 레코드를 반대 순서로 잡으려고 **서로 기다리면서** 생겼다. SKIP LOCKED는 잠긴 행을 기다리지 않고 건너뛰므로, 조회 단계에서 대기가 생기지 않고 원형 대기도 만들어지지 않았다.
2. **빨라진 이유:** 비관적 락은 코드가 남아 있는 동안 모든 요청이 맨 앞 미할당 행 하나에 줄을 섰다. SKIP LOCKED는 각 요청이 서로 다른 행을 바로 잡아 할당이 병렬로 진행됐다. 그 결과 매진도 더 빨리 확정됐다.
3. **꼬리 지연(p95·p99)은 세 방식이 비슷하다.** 스레드 100개가 커넥션 10개를 나눠 쓰므로, 꼬리 지연의 대부분은 잠금이 아니라 **커넥션 대기**로 보인다. 잠금 방식의 차이는 p50과 처리량에서 드러났다. 커넥션 풀 크기를 바꿔 가며 측정하면 이 부분을 분리할 수 있다.
4. **가짜 매진은 관찰되지 않았다.** SKIP LOCKED는 이론상 "남은 코드가 잠깐 잠겨 있을 뿐인데 매진으로 응답"할 수 있다(잠근 트랜잭션이 롤백되는 경우). 이번 측정에서는 모든 실행이 코드를 정확히 다 할당하고 끝났다. 롤백이 거의 없는 조건이었기 때문이다. 롤백이 잦아지는 조건(예: 같은 사용자 동시 요청이 많은 경우)에서는 다시 확인한다.

## 한계

- 노트북의 컨테이너 DB, 애플리케이션 1개, HTTP를 거치지 않은 측정이다. 절대값보다 방식 간 차이를 본다.
- 방식별 측정 횟수가 1~2회라 편차를 충분히 보지 못했다.
- 여러 인스턴스 환경과 HTTP 경유 부하(k6)는 2·3단계에서 같은 시나리오로 다시 측정한다.
