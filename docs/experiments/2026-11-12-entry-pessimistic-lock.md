# 실험 기록: 응모 할당에 비관적 락 적용 (2026-11-12)

선착순 응모의 갱신 손실을 비관적 락(`SELECT ... FOR UPDATE`)으로 막았을 때 정확성, 처리량, 지연이 어떻게 바뀌는지 측정했다. 3단계(사례 1)의 방식별 비교에서 기준점으로 쓴다.

## 바꾼 것

| 구분 | 잠금 없음 (변경 전, 커밋 4d02022) | 비관적 락 (변경 후) |
| --- | --- | --- |
| 미할당 코드 조회 | `findFirstByDropEventIdAndAssignedUserIdIsNullOrderByIdAsc` | 같은 조건 + `@Lock(PESSIMISTIC_WRITE)` → `... ORDER BY id LIMIT 1 FOR UPDATE` |
| 같은 사용자 중복 | 처리 없음 | `UNIQUE(drop_event_id, assigned_user_id)` 충돌 시 기존 당첨을 다시 조회해 반환 (`ParticipationService`) |

## 측정 환경

- MacBook, CPU 8코어. MySQL 8.4는 Testcontainers(OrbStack) 컨테이너.
- 애플리케이션 1개. HTTP를 거치지 않고 `ParticipationService.enter`를 스레드 풀에서 직접 호출.
- HikariCP 최대 커넥션 10개(기본값). 스레드가 10개보다 많으면 나머지는 커넥션을 기다린다. 지연 시간에는 이 대기 시간이 포함된다.
- 모든 요청을 `CountDownLatch`로 동시에 출발시켰다. 사용자는 미리 만들어 두었다.
- 실행: `STRESS=true ./gradlew concurrencyTest --tests '*EntryStressTests'`
- 한 번씩 측정했다(S3만 두 번). 노트북 환경이라 절대값보다는 두 방식의 차이를 본다.

- 두 방식 모두 DB에 할당된 코드 수는 정확히 코드 수와 같았다. 잠금 없는 방식은 DB는 맞지만 **응답이 틀렸다**. 같은 코드를 여러 명에게 "당첨"으로 알려 주고, 마지막에 UPDATE한 사람만 DB에 남았다.
- 비관적 락에서는 당첨 응답 수 = 코드 수, 모든 당첨자의 코드가 DB에서도 본인 것이었다.

## 해석

1. **정확성:** 비관적 락으로 갱신 손실이 사라졌다. 5,000건 규모에서도 남의 코드를 받은 당첨자가 0명이었다.
2. **처리량이 오히려 조금 올랐다 (약 15~20%).** 잠금 없는 방식은 매진 전까지 훨씬 많은 요청이 "당첨"으로 처리되며 UPDATE를 일으켰다. 같은 행에 몰린 UPDATE들이 서로의 행 잠금을 기다렸다. 비관적 락은 매진이 빨리 확정되고, 매진 응답은 쓰기 없이 끝나서 전체 작업량이 줄었다.
3. **꼬리 지연(p95·p99)은 비슷하다.** 맨 앞 미할당 행에 줄을 서는 구조라, 코드가 남아 있는 동안의 요청은 차례로 처리된다. 커넥션 10개 제한도 꼬리 지연에 영향을 준다.
4. **새 문제: 데드락.** 1,000~5,000건마다 6~15건(약 0.1~1.5%)이 `Deadlock found when trying to get lock`으로 실패했다.
   - 원인(추정): `FOR UPDATE`가 `(drop_event_id, assigned_user_id, id)` 인덱스 범위에 넥스트키 락을 건다. 할당하면서 인덱스 컬럼인 `assigned_user_id`가 바뀌어 인덱스 레코드가 이동한다. 그래서 잠금을 잡는 순서가 트랜잭션마다 엇갈린다. 정확한 잠금 순서는 `SHOW ENGINE INNODB STATUS`로 확인해야 한다.
   - 영향: 데이터는 틀리지 않는다(롤백된다). 하지만 해당 사용자는 당첨도 매진도 아닌 오류(현재 500)를 받는다. 코드가 남아 있는데 데드락으로 기회를 잃는 사용자가 생길 수 있다.
5. **Hibernate가 모든 컬럼을 UPDATE한다.** 할당 시 `code_ciphertext`, `code_hash`까지 다시 쓴다(`@DynamicUpdate` 없음). 잠금 구간과 쓰기 양을 늘리는 요인이다.
