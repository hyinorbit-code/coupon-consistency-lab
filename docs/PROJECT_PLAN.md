# 프로젝트 계획

작성일: 2026-10-30 (Asia/Seoul)
상태: 방향 확정, 업무 세부 규칙과 구현 도구는 0단계에서 확정
개정: 2026-10-30 전면 재작성 (목표 회사군, 단계 비중, 서비스 분리 실험 반영)

## 1. 배경

B2B 설치형 보안 솔루션 회사에서 4년간 Java/Spring 백엔드를 개발했다. 실무에서 확보한 것과 비어 있는 것은 다음과 같다.

| 구분 | 내용 |
| --- | --- |
| 실무로 확보 | Spring Boot 3·Java 21 멀티모듈 신규 솔루션 설계, Spring Data JPA·QueryDSL, MyBatis SQL 튜닝, 배치·스케줄러, 이중화 환경의 중복 실행·DeadLock 해결, 분석 서버 분산 구조, 보안 요건(RBAC·암호화) |
| 비어 있음 | 테스트 코드와 테스트 기준, 컨테이너·CI/CD·클라우드 배포, Redis, Kafka, DB 레벨 동시성 제어(락·버전), 정량적 성능·장애 검증 |

이 프로젝트는 비어 있는 부분을 채우고, 실무 경험(이중화·동시성 문제 해결, 프로세스 내부 이벤트 기반 처리)을 최신 스택과 정량 실험으로 확장하는 것을 목표로 한다. JPA는 새로 배우는 대상이 아니라 락 전략·트랜잭션 경계·쿼리 수 측정까지 **심화**하는 대상이다.

회사 코드·설정·고객 정보는 이 저장소에 옮기지 않는다.

## 2. 목표

### 2.1 최종 목표
업종과 무관하게 중견기업 이상 백엔드 포지션에서 통하는 **균형형 역량**을 증명한다. 면접에서 정합성·성능·안정성 세 축 모두에 대해 "직접 재현하고 측정하고 판단한" 근거로 답할 수 있어야 한다.

### 2.2 핵심 사례 3개 (비중 동일)

| 사례 | 질문 | 면접 축 |
| --- | --- | --- |
| 동시성 | 여러 API 인스턴스에서도 초과·중복 발급과 중복 사용을 막을 수 있는가? 제어 방식별 정확성·처리량·지연은 어떻게 다른가? | 정합성 |
| 성능 | 데이터와 요청이 늘 때 병목은 어디인가? 인덱스·쿼리·캐시 변경 전후가 수치로 어떻게 달라지는가? | 성능 |
| 장애 복구 | 종료·중복 전달·컨슈머 중단 이후에도 사용·정산 결과가 정확히 한 번만 반영되는가? | 안정성 |

선착순 발급 동시성은 흔한 주제이므로 짧고 깊게 다루고, 성능과 장애 복구에 같은 무게를 둔다.

### 2.3 성공 기준
- 발급·사용·취소·만료·정산 업무 규칙을 단위·통합 테스트로 검증한다.
- 1단계부터 CI에서 테스트가 자동 실행되고, 컨테이너 기반으로 배포·롤백할 수 있다.
- 다중 API 인스턴스에서 초과 발급과 중복 발급·사용이 없음을 부하 실험으로 확인한다.
- 동일 환경에서 성능 개선 전후의 p95/p99·처리량·오류율·자원 사용을 비교한다.
- 중복 이벤트, 처리 중 종료, 컨슈머 중단 뒤에도 기준 원장과 정산 결과가 일치한다.
- 다른 사람이 로컬 실행·배포·부하·장애 실험을 재현할 수 있다.
- 핵심 사례 문서 3개, ADR, 정직한 README를 남긴다.

성능 목표 수치는 기준 측정 뒤에 정한다. 목표는 성과가 아니며, 측정하지 않은 숫자는 어디에도 쓰지 않는다.

### 2.4 정직성 원칙
- 실사용자 트래픽 운영 경험은 이 프로젝트로 대체할 수 없다. 이력서에는 "통제된 부하·장애 실험"으로 명시한다.
- 실험 결과와 실제 서비스 운영 경력을 구분한다.
- 실패한 가설도 원인을 설명하면 유효한 결과로 기록한다.

## 3. 범위

### 3.1 최소 기능
- 관리자: 캠페인, 발급 수량, 발급·사용 기간, 쿠폰 혜택 설정
- 사용자: 발급, 보유 내역 조회, 사용 요청, 사용 취소
- 업무 처리: 초과·중복 발급 방지, 중복 사용 방지, 만료
- 정산: 사용·취소 내역을 기준 원장으로 기록하고 가맹점별 집계, 원장 대비 대사(reconciliation)
- 운영: 실패한 비동기 작업 조회·재처리, 로그·지표·추적

정산은 "중복·누락 없는 최종 일치"를 증명하는 데까지 다룬다. 복식부기 원장 등 회계 수준의 정산 설계는 범위에 넣지 않는다.

### 3.2 제외
실제 PG 연동과 금전 지급, 전체 쇼핑몰, 추천·검색·채팅, 복잡한 프론트엔드, 인증 플랫폼 자체 구축, 처음부터의 마이크로서비스 구성. 최소한의 인증·권한과 입력 검증은 포함한다.

## 4. 0단계에서 확정할 업무 규칙

구현 전에 사례와 불변식을 작성하고 확정안을 ADR(docs/decisions/)로 기록한다.

- 사용자별 발급 제한, 발급·사용 요청의 멱등키 범위와 유효기간
- 발급 취소 허용 여부와 수량 복원 여부
- 사용 취소 시 재사용 허용 여부, 만료 이후 취소 처리
- 캠페인 기간·쿠폰 만료 시각의 경계, 저장·표시 시간대
- 정산 기준: 사용액·할인액·부담액 중 무엇을 집계하는지
- 정산 마감 시점, 늦게 도착한 취소·이벤트의 조정 방식
- 상태 전이: 발급·사용·만료·취소의 허용 경로와 경합 시 우선순위
- 가맹점·사용자의 최소 권한, 실험용 계정 발급 방식

최소 불변식 후보: 발급량 ≤ 허용 수량, 사용자별 발급 제한 준수, 동일 사용의 유효 정산 반영은 정확히 한 번, 재처리 전후 최종 정산 일치.

## 5. 아키텍처 방향

### 5.1 모듈러 모놀리스로 시작
하나의 저장소, 하나의 Spring Boot 애플리케이션으로 시작한다. 발급·사용·정산의 경계는 패키지 또는 Gradle 모듈로 명확히 나누고, 모듈 간 의존 방향을 규칙으로 정한다. 관계형 DB를 정합성의 기준으로 삼는다.

### 5.2 기술은 관찰한 문제가 있을 때 도입
| 기술 | 도입 조건 | 도입 시점 |
| --- | --- | --- |
| DB 락·버전·조건부 UPDATE | 다중 인스턴스 동시 발급 재현 | 3단계 |
| Redis | 측정된 읽기 병목 또는 동시성 제어 대안 비교 | 3~4단계 |
| Kafka + Outbox 등 | 후속 집계·정산의 독립 처리 필요, DB 변경과 이벤트 발행 사이 실패 재현 | 5단계 |
| 서비스 분리, Gateway, 서킷브레이커 | 비동기 경계가 확인된 지점에서만, 선택 실험 | 7단계 |
| Kubernetes | 필요가 입증될 때만 검토 | 미정 |

비동기 처리를 붙였다는 이유로 API 응답을 업무 완료로 오해하지 않도록 접수·완료·실패 상태와 조회 계약을 정의한다. 큐로 옮긴 처리의 적체와 최종 완료 지연도 측정한다.

### 5.3 Spring Cloud에 대한 입장
Netflix 계열(Hystrix, Ribbon, Zuul)은 사용하지 않는다. 서비스 분리 실험에서 필요한 경우에만 Spring Cloud Gateway, Resilience4j, Micrometer Tracing(또는 OpenTelemetry)을 사용한다. 서비스 디스커버리·설정 서버는 컨테이너 환경 기본 기능으로 충분한지 먼저 검토한다.

## 6. 단계별 진행

| 단계 | 구현·실험 | 완료 기준 |
| --- | --- | --- |
| 0. 규칙·기반 결정 | 업무 규칙, 도구·버전, 테스트 전략 | 4절 확정, 초기 기술 선택 ADR |
| 1. 기본 기능 + 테스트 | 발급·사용·취소·만료, 기준 원장과 기본 정산 | 핵심 규칙 단위 테스트와 실제 DB 통합 테스트 통과, 로컬 실행 가능 |
| 2. 배포 자동화 | 컨테이너, CI(테스트 자동 실행), 클라우드 배포, 기본 로그·지표 | 커밋부터 배포까지 자동화, 롤백 절차 검증 |
| 3. 동시성 | 다중 API 인스턴스, 조건부 UPDATE·비관적 락·낙관적 락·Redis 등 비교 | 초과·중복 없음 확인, 방식별 정확성·처리량·지연 기록 (사례 1) |
| 4. 성능 | 데이터 증가, 실행계획, N+1·쿼리 수, 인덱스, 캐시 | 동일 조건의 개선 전후 지표 확보 (사례 2) |
| 5. 비동기 | Kafka, DB-이벤트 발행 연계, 멱등 소비 | 실패 모드별 중복·누락 처리 검증 |
| 6. 복구·대사 | 종료·중단·재실행, 정산 배치 재실행, 원장 대사 | 최종 결과 일치, 재현 가이드 (사례 3) |
| 7. 서비스 분리 실험 (선택) | 비동기 경계(예: 정산 워커)에서 서비스 하나만 분리, Gateway, 타임아웃·재시도·서킷브레이커, 분산 추적 | 분리 전후의 지연·장애 전파·운영 비용 비교 ADR. "분리하지 않는다"도 유효한 결론 |

각 단계의 완료 기준을 통과한 뒤 다음 단계로 넘어간다. 기능을 넓히기보다 실험 깊이를 확보한다. 달력 일정과 주당 투입 시간은 0단계에서 정한다.
