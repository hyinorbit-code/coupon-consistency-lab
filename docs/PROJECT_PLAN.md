# 프로젝트 계획

작성일: 2026-10-30 (Asia/Seoul)
상태: 방향 확정, 기술 스택(ADR-0001)·도메인(ADR-0002)·0단계 업무 규칙(ADR-0003)·테스트 전략(ADR-0004) 확정
개정: 2026-10-30 전면 재작성 (목표 회사군, 단계 비중, 서비스 분리 실험 반영)
개정: 2026-10-30 마일스톤 분할, 업무 규칙 확정 시점 구분, 초기 기술 스택 ADR 추가
개정: 2026-10-30 도메인을 선착순 무료 드롭으로 전환, 실전 이벤트 단계 추가(ADR-0002)

## 1. 배경

B2B 설치형 보안 솔루션 회사에서 4년간 Java/Spring 백엔드를 개발했다. 실무에서 확보한 것과 비어 있는 것은 다음과 같다.

| 구분 | 내용 |
| --- | --- |
| 실무로 확보 | Spring Boot 3·Java 21 멀티모듈 신규 솔루션 설계, Spring Data JPA·QueryDSL, MyBatis SQL 튜닝, 배치·스케줄러, 이중화 환경의 중복 실행·DeadLock 해결, 분석 서버 분산 구조, 보안 요건(RBAC·암호화) |
| 비어 있음 | 테스트 코드와 테스트 기준, 컨테이너·CI/CD·클라우드 배포, Redis, Kafka, DB 레벨 동시성 제어(락·버전), 정량적 성능·장애 검증, 실사용자 트래픽 운영 |

이 프로젝트는 비어 있는 부분을 채우고, 실무 경험(이중화·동시성 문제 해결, 프로세스 내부 이벤트 기반 처리)을 최신 스택과 정량 실험으로 확장하는 것을 목표로 한다. JPA는 새로 배우는 대상이 아니라 락 전략·트랜잭션 경계·쿼리 수 측정까지 **심화**하는 대상이다.

도메인은 **선착순 무료 드롭**이다. 오픈 시각을 공지하고 한정 수량의 경품 코드를 선착순으로 배포한다. 통제된 실험을 마친 뒤 커뮤니티에 공지해 실제 사용자 대상 이벤트를 운영한다(ADR-0002).

회사 코드·설정·고객 정보·장비는 이 프로젝트에 쓰지 않는다.

## 2. 목표

### 2.1 최종 목표
업종과 무관하게 중견기업 이상 백엔드 포지션에서 통하는 **균형형 역량**을 증명한다. 면접에서 정합성·성능·안정성 세 축 모두에 대해 "직접 재현하고 측정하고 판단한" 근거로 답할 수 있어야 하고, 그 판단을 실제 사용자 트래픽에서 검증한 결과를 남긴다.

### 2.2 핵심 사례 3개 (비중 동일)

| 사례 | 질문 | 면접 축 |
| --- | --- | --- |
| 동시성 | 여러 API 인스턴스에서도 경품 코드가 수량을 넘거나 중복 할당되지 않는가? 제어 방식별 정확성·처리량·지연은 어떻게 다른가? | 정합성 |
| 성능 | 오픈 시각의 순간 피크와 남은 수량 조회 폭주에서 병목은 어디인가? 쿼리·인덱스·캐시·대기열 변경 전후가 수치로 어떻게 달라지는가? | 성능 |
| 장애 복구 | 처리 중 종료·중복 전달·컨슈머 중단 이후에도 당첨과 코드 할당이 정확히 한 번만 반영되는가? | 안정성 |

실전 이벤트는 세 사례의 결론을 실제 트래픽에서 검증하는 단계다.

### 2.3 성공 기준
- 참여·당첨·코드 할당·조회 업무 규칙을 단위·통합 테스트로 검증한다.
- 1단계부터 CI에서 테스트가 자동 실행되고, 컨테이너 기반으로 배포·롤백할 수 있다.
- 다중 API 인스턴스에서 수량 초과와 중복 할당이 없음을 부하 실험으로 확인한다.
- 동일 환경에서 성능 개선 전후의 p95/p99·처리량·오류율·자원 사용을 비교한다.
- 중복 요청, 처리 중 종료, 컨슈머 중단 뒤에도 당첨 기록과 코드 할당 결과가 일치한다.
- 실전 이벤트에서 수량 초과·중복 할당 0건을 확인하고, 실측 트래픽·사전 부하 테스트와의 차이·장애 여부·차단한 어뷰징을 회고로 남긴다.
- 다른 사람이 로컬 실행·배포·부하·장애 실험을 재현할 수 있다.
- 핵심 사례 문서 3개, 이벤트 회고, ADR, 정직한 README를 남긴다.

성능 목표 수치는 기준 측정 뒤에 정한다. 목표는 성과가 아니며, 측정하지 않은 숫자는 어디에도 쓰지 않는다.

### 2.4 정직성 원칙
- 소규모 실사용자 이벤트를 운영하되, 실측 결과와 통제된 실험 결과를 구분해 기록한다. 이력서에도 "실사용자 N명 이벤트 실측"과 "통제된 부하·장애 실험"을 나눠 쓴다.
- 실제 참여자 수를 부풀리지 않는다. 규모가 작아도 실측값 그대로 쓴다.
- 실험 결과와 실제 서비스 운영 경력을 구분한다.
- 실패한 가설과 이벤트 당일 장애도 원인을 설명하면 유효한 결과로 기록한다.

## 3. 범위

### 3.1 최소 기능
- 관리자: 이벤트(오픈·종료 시각, 경품 설명) 생성, 경품 코드 등록, 결과·통계 조회
- 사용자: 카카오 로그인, 이벤트 상태·남은 수량 조회, 참여, 당첨 시 경품 코드(바코드) 조회, 카카오톡 공유
- 업무 처리: 선착순 판정, 수량 초과·중복 할당 방지, 계정당 1회 참여
- 대사: 당첨 기록과 코드 할당의 일치 검증
- 운영: 요청 속도 제한, 실패한 비동기 작업 조회·재처리, 로그·지표·추적, 이벤트 당일 대시보드
- 화면: 이벤트 페이지와 당첨 화면 수준의 단순한 웹 페이지

### 3.2 제외
할인 계산·가맹점·정산, 실제 결제와 금전 지급, 서버발 카카오톡·문자 발송(알림톡·기프티콘 발송 API 포함), 휴대폰 본인인증, 복잡한 프론트엔드, 인증 플랫폼 자체 구축, 처음부터의 마이크로서비스 구성. 최소한의 인증·권한과 입력 검증은 포함한다.

## 4. 업무 규칙 확정

구현 전에 사례와 불변식을 작성하고 확정안을 ADR(docs/decisions/)로 기록한다. 0단계가 길어지지 않도록 1차 마일스톤(1~3단계)에 필요한 규칙만 먼저 확정하고, 나머지는 해당 단계 직전에 확정한다.

0단계에서 확정 (1차 마일스톤에 필요) → ADR-0003에서 확정:
- 참여 제한과 참여 요청의 멱등성
- 선착순 판정 기준(어느 시각·순서로 판정하는지), 오픈 전·종료 후 요청 처리
- 당첨과 코드 할당의 관계(같은 트랜잭션 여부), 매진 처리
- 시간 경계와 저장·표시 시간대
- 경품 코드 보관(암호화)과 조회 권한
- 관리자·사용자 권한, 실험용 계정 발급 방식

E단계 직전에 확정:
- 대기열 도입 여부, 요청 속도 제한 기준, 봇·다중 계정 대응
- 개인정보 보관 기간과 파기 절차, 이벤트 공지·약관 문구

5~6단계 직전에 확정:
- 참여 접수를 비동기로 전환할지, 전환 시 접수·판정·실패 상태와 조회 계약

최소 불변식 후보: 할당된 코드 수 ≤ 등록된 코드 수, 코드 하나는 최대 한 명에게, 사용자당 이벤트별 당첨 최대 1회, 당첨 기록과 코드 할당은 항상 함께 존재, 재처리·재시작 전후 당첨자 집합 불변.

## 5. 아키텍처 방향

### 5.1 모듈러 모놀리스로 시작
하나의 저장소, 하나의 Spring Boot 애플리케이션으로 시작한다. 이벤트·참여·경품 코드의 경계는 패키지로 나누고 Spring Modulith로 모듈 간 의존 규칙을 테스트에서 검증한다(ADR-0001). 관계형 DB를 정합성의 기준으로 삼는다.

### 5.2 기술은 관찰한 문제가 있을 때 도입
| 기술 | 도입 조건 | 도입 시점 |
| --- | --- | --- |
| DB 락·조건부 UPDATE·`SKIP LOCKED` | 다중 인스턴스 동시 참여 재현 | 3단계 |
| Redis 캐시 | 남은 수량·이벤트 상태 조회의 측정된 읽기 병목 | 4단계 |
| Redis 기반 수량 제어 | DB 방식과의 정확성·처리량 비교 | 3~4단계 |
| 대기열 | 사전 부하 테스트에서 피크를 직접 처리하지 못함이 확인될 때 | E단계 준비 |
| Kafka + Outbox 등 | 참여 접수의 비동기 처리 필요, DB 변경과 이벤트 발행 사이 실패 재현 | 5단계 |
| 서비스 분리, Gateway, 서킷브레이커 | 비동기 경계가 확인된 지점에서만, 선택 실험 | 7단계 |
| Kubernetes | 필요가 입증될 때만 검토 | 미정 |

비동기 처리를 붙였다는 이유로 API 응답을 업무 완료로 오해하지 않도록 접수·완료·실패 상태와 조회 계약을 정의한다. 큐로 옮긴 처리의 적체와 최종 완료 지연도 측정한다.

돈이 걸린 상태 변경(코드 할당)은 시스템 안에서 정확히 한 번만 일어나게 하고, 화면 표시·공유 같은 전달은 중복돼도 손실이 없게 분리한다(ADR-0002).

### 5.3 Spring Cloud에 대한 입장
Netflix 계열(Hystrix, Ribbon, Zuul)은 사용하지 않는다. 서비스 분리 실험에서 필요한 경우에만 Spring Cloud Gateway, Resilience4j, Micrometer Tracing(또는 OpenTelemetry)을 사용한다. 서비스 디스커버리·설정 서버는 컨테이너 환경 기본 기능으로 충분한지 먼저 검토한다.

## 6. 단계별 진행

| 단계 | 구현·실험 | 완료 기준 |
| --- | --- | --- |
| 0. 규칙·기반 결정 | 업무 규칙, 도구·버전, 테스트 전략, 개발 환경, 프로젝트 골격 | 4절 중 0단계 규칙 확정, 초기 기술 선택 ADR, 테스트 전략 ADR, Testcontainers MySQL로 빈 통합 테스트 통과 |
| 1. 기본 기능 + 테스트 | 이벤트·코드 등록, 참여·선착순 판정·코드 할당, 당첨 조회, 기본 대사 | 핵심 규칙 단위 테스트와 실제 DB 통합 테스트 통과, 로컬 실행 가능 |
| 2. 배포 자동화 | 컨테이너, CI(테스트 자동 실행), 클라우드 배포, 기본 로그·지표 | 커밋부터 배포까지 자동화, 롤백 절차 검증 |
| 3. 동시성 | 다중 API 인스턴스, 조건부 UPDATE·비관적 락·`SKIP LOCKED`·Redis 등 비교 | 수량 초과·중복 할당 없음 확인, 방식별 정확성·처리량·지연 기록 (사례 1) |
| 4. 성능 | 오픈 시각 피크, 남은 수량 조회 폭주, 실행계획, 쿼리 수, 인덱스, 캐시 | 동일 조건의 개선 전후 지표 확보 (사례 2) |
| E. 실전 이벤트 | 카카오 로그인, 요청 속도 제한, 이벤트·당첨 화면, (필요 시) 대기열, 사전 부하 테스트, 1회차 리허설, 2회차 본 이벤트 | 실측 트래픽과 사전 부하 테스트 비교, 수량 초과·중복 할당 0건 확인, 이벤트 회고 |
| 5. 비동기 | Kafka, DB-이벤트 발행 연계, 멱등 소비 | 실패 모드별 중복·누락 처리 검증 |
| 6. 복구·대사 | 종료·중단·재실행, 재처리, 당첨·할당 대사 | 최종 결과 일치, 재현 가이드 (사례 3) |
| 7. 서비스 분리 실험 (선택) | 비동기 경계에서 서비스 하나만 분리, Gateway, 타임아웃·재시도·서킷브레이커, 분산 추적 | 분리 전후의 지연·장애 전파·운영 비용 비교 ADR. "분리하지 않는다"도 유효한 결론 |

각 단계의 완료 기준을 통과한 뒤 다음 단계로 넘어간다. 기능을 넓히기보다 실험 깊이를 확보한다. 주당 투입 시간과 요일 패턴은 고정하지 않고 시간이 날 때마다 진행하므로, 진행은 날짜가 아니라 단계별 완료 기준으로 판단한다.

### 6.1 마일스톤

재직 중에 코딩테스트·CS 준비와 병행하므로 전 단계를 끝낸 뒤 지원하지 않는다. 미완성 상태의 전 단계보다 끝까지 측정한 사례 하나가 면접에서 더 강하다.

목표 기간은 참고용이며 일정 압박을 위해 범위를 줄이거나 단계를 건너뛰지 않는다.

| 마일스톤 | 단계 | 목표 기간 | 결과 |
| --- | --- | --- | --- |
| 0단계 | 0 | 1~2주 | 4절 중 0단계 규칙, 초기 기술 스택 ADR(ADR-0001) 확정. 기획 문서를 다듬는 데 시간을 더 쓰지 않는다 |
| 1차 | 1~3 | 6~8주 | 테스트·배포 자동화·DB 동시성 제어·정량 측정 갭 해소, 사례 1 문서. 이 시점에 이력서에 반영하고 지원을 시작한다 |
| 2차 | 4, E | 지원과 병행 | 사례 2, 실전 이벤트 회고. 실사용자 트래픽 실측 결과를 이력서에 추가한다 |
| 3차 | 5~6 | 지원과 병행 | 사례 3 |
| 선택 | 7 | 미정 | 투입 대비 면접 가치가 가장 낮아 사실상 제외. 여유가 생길 때만 진행 |

기존 경력의 성과 수치 복원과 설계 판단 정리는 이 프로젝트와 같은 주에 병행한다.

### 6.2 실전 이벤트 운영 원칙

- 회차당 경품 예산은 약 2만 원(2천 원 커피 쿠폰 10매)으로 시작하고, 1회차 결과를 보고 2회차 규모를 정한다.
- 이벤트 전에 예상 트래픽의 여러 배로 같은 인프라에 사전 부하 테스트를 수행해 한계를 먼저 측정한다.
- 이벤트 시간에만 인프라를 늘리고 종료 후 줄인다. 인프라 비용은 별도로 기록한다.
- 사전 확인: 회사 취업규칙의 겸업·외부 활동 조항, 홍보할 커뮤니티의 홍보 글 규정, 개인정보 처리방침과 보관 기간 공지.
- 당일 운영: 대시보드 감시, 장애 대응 절차와 중단 기준을 미리 정한다.

## 7. 최종 산출물

- README: 목적, 실행법, 구조, 실제 측정 성과와 한계
- 동시성 사례: 문제·대안·정확성·성능·결정
- 성능 사례: 병목·근거·개선·동일 조건 비교·비용
- 장애 복구 사례: 실패 지점·복구·재처리·최종 데이터 검증
- 실전 이벤트 회고: 참여자 수·피크 RPS 실측, 사전 부하 테스트와의 차이, 장애·대응, 어뷰징 차단, 대사 결과, 비용
- (선택) 서비스 분리 판단 ADR
- 코드, 테스트, 데이터 생성·부하·장애 스크립트, 환경 명세, 결과 요약

이력서에 들어갈 참여자 수·서버 수·요청 수·p95·오류율은 실제 결과가 확보된 뒤 채운다.
